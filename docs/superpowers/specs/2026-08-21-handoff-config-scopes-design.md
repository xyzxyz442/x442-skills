# Handoff configuration scopes — design

Date — 2026-08-21
Status — approved, pre-implementation
Branch — `feature/handoff-config-scopes`

## Problem

Configuration for the handoff board is split across two mechanisms with no stated rule for which
owns what, one of them silently does not work, and the format itself is a code-execution vector
across a trust boundary.

**1. A board-wide knob cannot be set in the board's own config.** `$BOARD/config` is committed,
generated by `setup-handoff`, and sourced by both `handoff` and `hooks.sh`. It looks like the
settings file, and for most keys it is one. But `HANDOFF_TTL_HOURS` is captured _before_ the file
is read:

|                           | `handoff` | `hooks.sh` |
| ------------------------- | --------- | ---------- |
| reads `HANDOFF_TTL_HOURS` | line 14   | line 29    |
| sources `config`          | line 30   | line 57    |

Verified against a scratch board — `HANDOFF_TTL_HOURS=99` in `config` claims for **4h**; the same
value in the environment claims for **99h**. Env-only means lease policy cannot be a committed team
decision: every person would have to export it, and hooks invoked by the tool will not reliably
inherit a shell export.

The bug is confined to this one knob. `HANDOFF_ALLOW_VERIFY_CMD` is read at its point of use
(line 1071), well after the config source, and the installer already writes it to `config` — so it
behaves correctly today and is the model to follow.

**2. Per-repo identity is baked into the hook command as environment.** `merge-hooks.py` builds

```text
HANDOFF_REPO=... HANDOFF_HDPATH=... HANDOFF_GROUP=... bash .../hooks.sh --kind ... --tool ...
```

Environment should be an override for a one-off run, not the carrier of normal operating
configuration. Configuration baked into a command string is invisible to anyone reading the board,
cannot be reviewed as a committed file, and goes stale silently when a repo is renamed or moved.

**3. A shell config on a shared board is arbitrary code execution.** `write_board_config` is run by
**every member repo's installer** on a cross-repo board, and each member then `. "$DIR/config"`s the
result. A value like `TOPOLOGY=$(...)` written by one repo executes in every sibling's shell, in
their hooks, on every tool call. The file crosses a trust boundary by design, and sourcing is the
wrong way to read it.

## The constraint that shapes the design

Identity cannot simply move into the board config. `merge-hooks.py` states why:

> _"bake this consuming repo's identity into the command so hooks.sh reads `$HANDOFF_REPO` instead
> of the shared config's `REPO_NAME` (which would be whoever installed last)."_

On a cross-repo board the board config is **shared by every member repo**. A per-consumer fact
written there is clobbered by the next repo to install. So moving identity out of the command
requires a second, repo-local scope — that is the structural change here, and the reason this is
not a one-line fix.

## Format — JSON

Config becomes JSON. Three reasons, in order of weight:

1. **It is data, not code.** This closes the execution vector in problem 3 outright.
2. **No key collisions.** The current code carries a workaround comment — `"NOT GROUPS — that is a
bash built-in array of the user's gids, e.g. 20, so a config key named GROUPS can never be read
back"`. JSON keys have no such hazard, and the workaround goes away.
3. **Consistency.** Every other config in this ecosystem is JSON — `.claude/settings.json`,
   `.github/hooks/handoff.json`, `.graph-repos.json`, `.handoff-repos.json`.

**Keys are camelCase.** The `HANDOFF_*` names stay as the environment override channel, so the two
are visually distinct: a `HANDOFF_` prefix always means "override", a camelCase key always means
"configured".

**Board** — `$BOARD/config.json`:

```json
{
  "topology": "single-repo",
  "repoName": "x442-skills",
  "groups": ["acme-svcs"],
  "groupLayout": "subfolder",
  "ttlHours": 4,
  "allowVerifyCmd": false
}
```

**Repo** — `$REPO/.agents/handoff.config.json`:

```json
{ "repo": "x442-skills", "group": "acme-svcs", "boardPath": "../workspace/src/.agents/handoff" }
```

### Cost — python3 becomes a runtime requirement

Today `handoff` uses `python3` **zero** times and `hooks.sh` carries deliberate `sed` fallbacks
(`"best-effort, no python3"`, `"sed-free fallback if python3 is gone"`) so a machine without it
degrades to advisory-only rather than failing. Reading JSON ends that for the JSON path.

This is accepted, not hidden:

- **Stated requirement.** Reading `config.json` without `python3` is a clear error naming the
  missing dependency — never a silent half-configured board.
- **`verify-setup-handoff.sh` checks it** and reports it as a FAIL when a `config.json` exists,
  rather than the current advisory `[warn]`.
- **Legacy boards stay python3-free.** The shell `config` reader is retained for back-compat (see
  Migration), so a board that has not migrated keeps working exactly as it does now.

Measured cost of a `python3` spawn on the target machine: **~125 ms**, against ~0 for sourcing.
Placement is chosen accordingly:

- **Hook path** — `pretool-edit` fires on every edit, but it **already** spawns `python3` to parse
  the hook payload. Config reading folds into that same spawn: marginal cost ≈ 0.
- **CLI path** — `handoff` goes from 0 to 1 spawn per invocation. That is a command run at claim and
  release time, not per keystroke, so ~125 ms is acceptable.
- **No generated shell sidecar.** A cached shell form would restore zero-dependency reads but
  introduces a second file that can drift from its source — which is the exact bug class in problem
  1. Not worth it until the CLI cost is shown to matter.

## Scopes

Four levels, nearest wins:

```text
env  >  repo config.json  >  board config.json  >  built-in default
```

- **env** — override only. One-off runs, debugging, CI. `HANDOFF_TTL_HOURS=1 handoff claim ID` keeps
  working, and env stays the escape hatch for anything a file cannot express.
- **repo config** — `$REPO/.agents/handoff.config.json`, committed, owned by the consuming repo.
  Holds this repo's identity in the board (`repo`, `group`, `boardPath`) plus any per-repo policy
  override. Written **only for cross-repo installs**; see below.
- **board config** — `$BOARD/config.json`, committed, board-global. Facts every member must agree on
  (`topology`, `groups`, `groupLayout`) plus board-wide policy defaults (`ttlHours`,
  `allowVerifyCmd`).
- **built-in default** — the value in the script.

**Single-repo installs get no repo config.** A single-repo board has exactly one consumer, so the
board config already serves both roles and there is nothing a second file would disambiguate. This
also keeps single-repo installs byte-identical to today, which the existing code deliberately
preserves (`"Empty (single-repo) => no prefix => byte-identical to the pre-existing command"`).

**One reader, sourced by both.** The precedence resolver ships as a new payload file,
`$BOARD/scripts/config.sh`, sourced by `handoff` and `hooks.sh`. It is not duplicated into each:
this payload already has four mirrored copies of `hooks.sh` across the repo and its fixtures, and
a hand-copied resolver in two files is exactly how those mirrors drift.

The resolver reads every scope in **one** `python3` invocation and emits shell assignments the
caller evaluates, so precedence is decided in one place rather than re-derived per knob.

## Documented, commented config

JSON has no comments, so discoverability moves to the two places that can carry it: the generated
`README.md` in the board (which the installer already writes) gains a table of every key, its
default, and its meaning; and `write_board_config` emits **every** key explicitly rather than
omitting defaulted ones, so the file itself shows the full surface.

This is why a `configure-*` skill family remains a **non-goal** — see below.

## Migration

Three migrations, all idempotent, all running on every `setup-handoff` install — the same pattern as
the flat-layout and legacy-path migrations already in that installer.

**A. Shell `config` → `config.json`.** If `config` exists and `config.json` does not, parse the
`KEY=value` lines and write the JSON equivalent. The legacy file is retained, not deleted, until the
next install proves the JSON is good; the readers prefer `config.json` and fall back to `config`.

**B. Env-prefixed hook command → repo `config.json`.** For each wired tool config:

1. Parse the leading `HANDOFF_*=value` assignments out of each managed hook command (`shlex`, so
   quoted values survive).
2. Write them to `$REPO/.agents/handoff.config.json`.
3. Rewrite the command without the prefix.

A command with no prefix is already migrated and is left untouched.

**The migration refuses to strip a prefix it cannot prove is safe.** Before rewriting, it resolves
the identity triple both ways — from the existing prefix, and from the repo config it just wrote —
and aborts that tool's rewrite unless they are identical. A repo silently switching sections would
mean filing handoffs where nobody reads them, which is worse than leaving a working prefix in place.

**C. Nothing breaks in the field.** Real boards exist — this repo's, and a shared cross-repo one. Every
reader accepts `config.json`, then legacy `config`, then defaults, so an un-migrated board keeps
working untouched.

## Identity resolution — declared becomes discovered

This is the change that carries real risk, so it is stated plainly.

Today identity is **declared** in the command string. After migration it is **discovered**:
`hooks.sh` resolves the consuming repo, then reads the config there. That is more robust to a repo
being renamed or moved — a baked-in `HANDOFF_REPO` goes stale with no error — but it regresses if a
tool ever invokes the hook with a working directory outside the repo.

Mitigation, in order of preference at runtime:

1. `--project-dir PATH` passed by the hook command, for tools that expand one. Claude already
   anchors the script path with `$CLAUDE_PROJECT_DIR`, so the value is available and costs nothing.
   A path flag says _where_, never _what_ — it is structurally different from carrying policy in
   env, and it keeps resolution deterministic rather than cwd-dependent.
2. `git rev-parse --show-toplevel` from the working directory.
3. No repo resolved — fall back to board config alone, which is correct for a standalone board
   operated directly.

## Testing

- **Red/green on the TTL bug** — `ttlHours` in board config is ignored before the change and honored
  after, asserted on the claim's reported expiry.
- **Precedence** — env beats repo config beats board config beats default, each step asserted.
- **Shell → JSON migration** — a legacy board migrates, and every resolved value is identical before
  and after.
- **Cross-repo migration** — a fixture wired with the legacy env prefix migrates to a repo config,
  and the resolved identity triple is **identical** before and after.
- **Refusal** — a prefix whose resolution would change is left in place, and the installer says so.
- **Malformed JSON** — a corrupt `config.json` fails loudly with the file named, and never silently
  falls through to defaults, which would change lease and section behavior without saying so.
- **No python3** — with `config.json` present, the CLI errors clearly; with only a legacy `config`,
  it still works.
- **Idempotency** — a second install leaves an empty diff, including on an already-migrated repo.
- **Single-repo unchanged** — a single-repo install writes no repo config and its hook commands stay
  byte-identical, guarding the property the current code calls out explicitly.

## Non-goals

**No `configure-*` skill family.** Applying this repo's own test — a skill earns existence when it
does something re-running or editing cannot — the user-facing policy surface is two scalars
(`ttlHours`, `allowVerifyCmd`). The rest of the keys are wiring facts the installer and cross-repo
sync own, or runtime-derived values. A skill whose entire job is assigning a documented number to a
documented key is a worse interface than a documented JSON file with a schema.

`setup-embeddings.sh` marks where the line actually is: it earns being a script because switching
provider **re-embeds every node in the graph** — consequential, multi-step, stateful. If a knob ever
gains consequences of that kind — switching board topology or layout, which must move docs and
rewrite every tool's hook command — that is the point to revisit a configure skill.
