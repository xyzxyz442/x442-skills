# Handoff configuration scopes — design

Date — 2026-08-21
Status — approved, pre-implementation
Branch — `feature/handoff-config-scopes`

## Problem

Configuration for the handoff board is split across two mechanisms with no stated rule for which
owns what, and one of them silently does not work.

**1. A board-wide knob cannot be set in the board's own config.** `$BOARD/config` is committed,
generated by `setup-handoff`, and sourced by both `handoff` and `hooks.sh`. It looks like the
settings file, and for most keys it is one. But `HANDOFF_TTL_HOURS` is captured _before_ the file
is read:

|                           | `handoff` | `hooks.sh` |
| ------------------------- | --------- | ---------- |
| reads `HANDOFF_TTL_HOURS` | line 14   | line 29    |
| sources `config`          | line 30   | line 57    |

Verified against a scratch board — `HANDOFF_TTL_HOURS=99` in `config` claims for **4h**; the same
value in the environment claims for **99h**. Env-only means lease policy cannot be a committed team
decision: every person would have to export it, and hooks invoked by the tool will not reliably
inherit a shell export.

The bug is confined to this one knob. `HANDOFF_ALLOW_VERIFY_CMD` is read at its point of use
(line 1071), well after the config source, and the installer already writes it to `config` — so it
behaves correctly today and is the model to follow.

**2. Per-repo identity is baked into the hook command as environment.** `merge-hooks.py` builds

```text
HANDOFF_REPO=... HANDOFF_HDPATH=... HANDOFF_GROUP=... bash .../hooks.sh --kind ... --tool ...
```

Environment should be an override for a one-off run, not the carrier of normal operating
configuration. Configuration baked into a command string is invisible to anyone reading the board,
cannot be reviewed as a committed file, and goes stale silently when a repo is renamed or moved.

## The constraint that shapes the design

Identity cannot simply move into `$BOARD/config`. `merge-hooks.py` states why:

> _"bake this consuming repo's identity into the command so hooks.sh reads `$HANDOFF_REPO` instead
> of the shared config's `REPO_NAME` (which would be whoever installed last)."_

On a cross-repo board, `$BOARD/config` is **shared by every member repo**. A per-consumer fact
written there is clobbered by the next repo to install. So moving identity out of the command
requires a second, repo-local scope — that is the structural change here, and the reason this is
not a one-line fix.

## Scopes

Four levels, nearest wins:

```text
env  >  repo config  >  board config  >  built-in default
```

- **env** — override only. One-off runs, debugging, CI. `HANDOFF_TTL_HOURS=1 handoff claim ID` keeps
  working, and env stays the escape hatch for anything a file cannot express.
- **repo config** — `$REPO/.agents/handoff.config`, committed, owned by the consuming repo. Holds
  this repo's identity in the board (`HANDOFF_REPO`, `HANDOFF_GROUP`, `HANDOFF_HDPATH`) plus any
  per-repo policy override. Written **only for cross-repo installs**; see below.
- **board config** — `$BOARD/config`, committed, board-global. Facts every member must agree on
  (`TOPOLOGY`, `HANDOFF_GROUPS`, `HANDOFF_GROUP_LAYOUT`) plus board-wide policy defaults
  (`HANDOFF_TTL_HOURS`, `HANDOFF_ALLOW_VERIFY_CMD`).
- **built-in default** — the value in the script.

**Single-repo installs get no repo config.** A single-repo board has exactly one consumer, so
`$BOARD/config` already serves both roles and there is nothing a second file would disambiguate.
This also keeps single-repo installs byte-identical to today, which the existing code deliberately
preserves (`"Empty (single-repo) => no prefix => byte-identical to the pre-existing command"`).

**Precedence is implemented by the pattern already correct in `handoff` two lines below the bug:**
set a default, source the config files nearest-last, then let env override:

```text
TTL_HOURS=4
. "$BOARD/config"          # board-wide default
. "$REPO/.agents/handoff.config"   # repo override, when present
TTL_HOURS="${HANDOFF_TTL_HOURS:-$TTL_HOURS}"   # env wins
```

This is exactly how `REPO_NAME="${HANDOFF_REPO:-$REPO_NAME}"` already behaves. The fix is to make
every knob follow it, not to invent a mechanism.

## Documented, commented config

`write_board_config` gains the tunables as commented-out lines carrying their defaults and a
one-line explanation each:

```text
# HANDOFF_TTL_HOURS=4          # hours a claim holds before it self-reaps
# HANDOFF_ALLOW_VERIFY_CMD=0   # 1 lets `release --run-verify` execute a command from a local doc
```

Discoverability lives in the file the user already has, not in a skill an agent may never load.
This is the reason a `configure-*` skill family is a **non-goal** — see below.

## Migration off the env-prefixed command

`setup-handoff` detects a legacy env prefix in any wired tool config, and migrates it:

1. Parse the leading `HANDOFF_*=value` assignments out of each managed hook command (`shlex`, so
   quoted values survive).
2. Write them to `$REPO/.agents/handoff.config`.
3. Rewrite the command without the prefix.

Idempotent — a command with no prefix is already migrated and is left untouched. The detection runs
on every install, so a repo wired by an older version migrates on its next `setup-handoff` run,
exactly like the flat-layout and legacy-path migrations already in that installer.

**The migration refuses to strip a prefix it cannot prove is safe.** Before rewriting, it resolves
the identity triple both ways — from the existing prefix, and from the repo config it just wrote —
and aborts that tool's rewrite unless they are identical. A repo silently switching sections would
mean filing handoffs where nobody reads them, which is worse than leaving a working prefix in place.

## Identity resolution — declared becomes discovered

This is the change that carries real risk, so it is stated plainly.

Today identity is **declared** in the command string. After migration it is **discovered**:
`hooks.sh` resolves the consuming repo, then reads the config there. That is more robust to a repo
being renamed or moved — a baked-in `HANDOFF_REPO` goes stale with no error — but it regresses if a
tool ever invokes the hook with a working directory outside the repo.

Mitigation, in order of preference at runtime:

1. `--project-dir PATH` passed by the hook command, for tools that expand one. Claude already
   anchors the script path with `$CLAUDE_PROJECT_DIR`, so the value is available and costs nothing.
   A path flag says _where_, never _what_ — it is structurally different from carrying policy in
   env, and it keeps resolution deterministic rather than cwd-dependent.
2. `git rev-parse --show-toplevel` from the working directory.
3. No repo resolved — fall back to board config alone, which is correct for a standalone board
   operated directly.

## Testing

- **Red/green on the TTL bug** — `HANDOFF_TTL_HOURS` in board config is ignored before the change
  and honored after, asserted on the claim's reported expiry.
- **Precedence** — env beats repo config beats board config beats default, each step asserted.
- **Cross-repo migration** — a fixture wired with the legacy env prefix migrates to a repo config,
  and the resolved identity triple is **identical** before and after.
- **Refusal** — a prefix whose resolution would change is left in place, and the installer says so.
- **Idempotency** — a second install leaves an empty diff, including on an already-migrated repo.
- **Single-repo unchanged** — a single-repo install writes no repo config and its hook commands stay
  byte-identical, guarding the property the current code calls out explicitly.

## Non-goals

**No `configure-*` skill family.** Applying this repo's own test — a skill earns existence when it
does something re-running or editing cannot — the user-facing policy surface is two scalars
(`HANDOFF_TTL_HOURS`, `HANDOFF_ALLOW_VERIFY_CMD`). The rest of the `HANDOFF_*` vars are wiring facts
the installer and cross-repo sync own, or runtime-derived values. A skill whose entire job is
assigning a documented number to a documented key is a worse interface than the commented config
file above.

`setup-embeddings.sh` marks where the line actually is: it earns being a script because switching
provider **re-embeds every node in the graph** — consequential, multi-step, stateful. If a knob ever
gains consequences of that kind — switching board topology or layout, which must move docs and
rewrite every tool's hook command — that is the point to revisit a configure skill.
